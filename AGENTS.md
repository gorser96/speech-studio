# Правила навигации для ИИ-агента

Область действия — мобильный проект `speechstudio-mobile`, расположенный в `src/speechstudio-mobile/`. Команды ниже выполняются из его корня (`src/speechstudio-mobile/`).

## Работа по спецификациям

- Используй OpenSpec: [процесс](openspec/README.md), [настройки](openspec/config.yaml).
  Если `openspec` отсутствует в PATH, вызывай `npx --yes @fission-ai/openspec@1.13.0`
  с теми же аргументами вместо `openspec` из инструкций навыков.
  Перед проектированием и реализацией прочитай [ARCHITECTURE.md](src/speechstudio-mobile/ARCHITECTURE.md),
  затем только относящиеся к задаче спецификации и изменение в `openspec/changes/`.
  Архитектура обязательна для решений; фактическое состояние проверяй по коду.
- Для изменения поведения кратко зафиксируй цель, критерии приёмки, затронутые
  возможности, техническое решение и задачи. Не дублируй сведения между артефактами.
  Уточняй существенные неоднозначности до реализации зависимой части.
- Актуальные контракты находятся в `openspec/specs/`; указатель — `openspec/README.md`.
  Результаты и незавершённая приёмка — в `openspec/verification/README.md`.
  Наличие требования в спецификации не означает подтверждённую реализацию.
- Для исправления ошибки проверь действующую спецификацию: если требование уже описано,
  не создавай дубликат; зафиксируй регрессию и проверку в задачах.
- Для документации, опечаток и рефакторинга без изменения поведения полный цикл не нужен.
- Проверяй результат по критериям приёмки. Обновляй спецификацию при согласованном
  изменении поведения; не подгоняй требования под ошибочную реализацию.
- Следуй выбранному пользователем этапу. Запрос на спецификацию или план сам по себе
  не означает запрос на реализацию. При разрешении полного цикла продолжай по этапам.
- Проектные документы пиши по-русски; служебные заголовки OpenSpec сохраняй
  в формате инструмента. Не создавай дополнительные исследования и чек-листы без нужды.

## Как искать код

1. Прочитай [PACKAGES.md](src/speechstudio-mobile/PACKAGES.md). Выбери пакет по задаче и открой его `PACKAGE.md`. Если пакет уже известен, можно сразу открыть его описание.
2. В `PACKAGE.md` найди точку входа, нужный файл, связи и ограничения. Читай только относящиеся к задаче исходники; описания служат картой, а текущий код — источником истины.
3. Если известно имя файла, используй `rg --files app/src -g '*Lesson*'`. Для символа или текста сначала ограничь поиск выбранным пакетом: `rg -n -g '*.kt' 'UpdateLesson|onSave' app/src/main/java/com/logoped_plus/ui/screen/schedule`. Для буквального текста используй `rg -n -F -g '*.kt' 'Выбрать видео' app/src/main/java`.
4. Проследи вызовы и данные: экран → callback/действие → ViewModel → интерфейс repository → реализация → модель. Перед переходом в другой пакет прочитай его `PACKAGE.md`. Проверяй вызывающий код и потребителей изменяемого контракта. Для расписания обязательно учитывай `ScheduleScreen.kt` в родительском пакете: там маршрутизация форм и черновики.
5. Если локальный поиск ничего не дал, расширяй его до родительского пакета, затем до `app/src/main`, после этого до `app/src`. Объявления пакетов можно проверить командой `rg -n '^package ' app/src -g '*.kt' -g '*.java'`. Отсутствие сущности в документации ещё не доказывает отсутствие кода.
6. Для поведения платформы проверь `app/src/main/AndroidManifest.xml` и `app/src/main/res`; для сборки — `settings.gradle.kts`, `build.gradle.kts`, `app/build.gradle.kts`, `gradle/libs.versions.toml`. Для тестов ищи в `app/src/test` и `app/src/androidTest`; ссылки на существующие тесты указаны в описаниях пакетов.
7. Поиск по всему проекту оставь на случай, когда более узкие области не помогли. Исключай `build`, `app/build`, `.gradle`, `.kotlin`, `.idea` и `.git`; не используй сгенерированные классы как место для правок. Пример: `rg -n -g '!**/build/**' -g '!.gradle/**' -g '!.kotlin/**' -g '!.idea/**' -g '!.git/**' 'LessonRepository' .`.
8. Перед изменением сформулируй найденную цепочку файлов и проверь фактическое поведение. [ARCHITECTURE.md](src/speechstudio-mobile/ARCHITECTURE.md) и [описание проекта.md](<описание проекта.md>) описывают в том числе планы: не считай Room, Hilt, Navigation Compose или use cases уже реализованными без подтверждения в исходниках и зависимостях.

## Поддержание карты

- Для каждого реально объявленного Kotlin/Java package поддерживай `PACKAGE.md` рядом с исходниками. Родительские каталоги без объявлений `package` не требуют отдельного описания.
- При добавлении или переносе файлов обновляй таблицу файлов, связи и ограничения затронутых описаний. При добавлении/удалении пакета обновляй также `PACKAGES.md`.
- Один и тот же package в `main`, `test`, `androidTest` описывается общей картой в `main`, со ссылками на тесты. Для нового пакета, существующего только в тестах, размещай описание в соответствующем тестовом каталоге и добавляй его в индекс.
- Пиши по-русски, сохраняй точные имена символов и относительные Markdown-ссылки. Не привязывай карту к номерам строк. Отмечай явно то, что ещё не реализовано; не превращай предположения в описание текущего поведения.

## Проверки после изменений

- Выбирай минимальные проверки по риску изменения и критериям приёмки. Сначала используй
  существующие тесты. Новый тест нужен для непокрытого существенного бизнес-правила,
  воспроизводимой регрессии или риска потери/повреждения данных.
- Проверяй правило на самом дешёвом достаточном уровне. Не дублируй один сценарий
  в repository, ViewModel и UI; не тестируй тривиальные getters, делегирование и детали
  реализации. Не вводи обязательный TDD, квоты покрытия или тест на каждый класс.
- Локально запускай затронутые тесты: `.\gradlew.bat :app:testDebugUnitTest --tests "полное.ИмяТеста"`.
  Весь набор `:app:testDebugUnitTest` нужен при широком влиянии или неясных границах регрессии.
  `:app:connectedDebugAndroidTest` запускай только для существенного Android/Room/UI-риска,
  который нельзя проверить локально, при наличии устройства/эмулятора.
- Для простой визуальной правки достаточно адресной ручной проверки; для документации —
  ссылок и `git diff --check`, без сборки. Охват `package` проверяй при изменении карты/структуры.
- Кратко сообщай, что проверено, результат и что не запускалось. Недоступная среда не означает
  успешную проверку. `Example*Test` не подтверждают пользовательские сценарии.
- Существующие полезные тесты сохраняй. Удаляй только доказанно дублирующие или устаревшие
  проверки в рамках затронутой задачи, а не ради уменьшения числа тестов.
